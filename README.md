# ne-vocab-exam-generator

어휘 시험지를 **HWP · HWPX · DOCX** 파일로 내보내는 브라우저용(클라이언트 사이드) 생성 엔진입니다.
서버·플러그인 없이 순수 JavaScript(ES5)로 한글(hwp/hwpx)·워드(docx) 문서를 만들어 다운로드합니다.

> **기여 범위 안내**
> 어휘 시험지 빌더 전체의 **UI/화면 목업은 팀 공동 작업**이며,
> 이 저장소에 담긴 **시험지 파일 다운로드(hwp·hwpx·docx) 기능은 본인(@ne-hrpark)이 개발**한 부분만 추려낸 것입니다.

## 설계 개요

- **하나의 데이터 모델 → 3포맷 공통 생성.** 문항 데이터(`groups`)와 서식 규칙(글자크기/줄간격/문항간격)을 `ne-export-common.js`에 SSOT로 두고 세 엔진이 공유합니다.
- **템플릿 본문교체 방식(HWPX/DOCX).** 레이아웃을 코드로 처음부터 조립하지 않고, 검증된 정본 샘플의 스타일·다단 정의를 추출·재사용하고 본문 문단만 데이터로 교체합니다. → 뷰어 호환성과 레이아웃 안정성 확보.
- **뷰어 호환.** 한글(HWP Office)에서 2단 다단·밑줄 연속선·헤더 점선박스가 안정적으로 렌더되도록 맞춤.

## 실행에 필요한 것

템플릿을 base64 JS(`templates.js`·`docx-templates.js`)로 내장했으므로, **`index.html`을 열면(로컬 `file://` 또는 GitHub Pages) 별도 준비 없이 HWP·HWPX·DOCX 다운로드가 모두 동작**합니다. 유일한 외부 의존은 CDN 라이브러리 두 개뿐이며 `index.html`이 자동으로 로드합니다.

```html
<script src="https://cdn.jsdelivr.net/npm/jszip@3.10.1/dist/jszip.min.js"></script>
<script src="https://cdn.jsdelivr.net/npm/docx@8.5.0/build/index.umd.js"></script>
```

> 실행에는 `templates.js`·`docx-templates.js`만 있으면 됩니다. 정본 원본(`templates/`·`docx/`)과 빌드 스크립트는 **정본이 바뀔 때 재생성하기 위한** 것으로, 아래 HOWTO를 따르세요.
>
> **상세 아키텍처·구현·잔여 과제(TODO)는 아래 [부록]에 통합**되어 있습니다.

## 정본이 바뀌면 — 재생성 HOWTO

시험지 **정본(레이아웃·여백·헤더 기준 파일)** 이 변경되면, 원본을 고치고 스크립트로 내장 JS를 다시 만듭니다. 실행은 Python만 있으면 되고, 한글/워드 라이선스는 필요 없습니다.

**HWPX 정본 변경 시**
```bash
# 1) templates/ 안의 해당 .hwpx 를 한글에서 열어 수정·저장 (또는 새 정본으로 교체)
# 2) 내장 JS 재생성
python tools/build-templates-js.py     # templates/*.hwpx → templates.js
```

**DOCX 정본 변경 시**
```bash
# 1) docx/{단}단/{크기}/ 의 해당 .docx 를 Word에서 수정·저장
# 2) 내장 JS 재생성
python tools/build-docx-templates.py   # docx/**/*.docx → docx-templates.js
```

- 재생성 후 `index.html`을 다시 열면 바뀐 정본이 반영됩니다. `templates.js`·`docx-templates.js`는 **자동 생성물이라 손으로 고치지 마세요**(다음 재생성 때 덮어써짐).
- `templates.js`만 있고 원본 폴더가 없을 때: `python tools/extract-templates-from-js.py`로 `templates/`를 복원한 뒤 수정 → 재생성.
- (선택) 재생성 결과가 기존과 어긋나지 않는지 검증: `validation/`의 `build.py`로 같은 조합을 Python 독립 생성해 바이트 대조(부록 §10 오라클).
- ⚠️ 줄간격 %는 HWPX 정본 **파일명**(`…(N%).hwpx`)과 물려 있어, 그 파일이 실재하는 범위에서만 조합을 바꿀 수 있습니다(부록 §9.1).

## 0. 이 프로젝트가 하는 일

영어 어휘 **시험지 파일**을 자동 생성한다. 단어형·파생어·유의어/반의어·문장완성·영영풀이 등 문항 데이터를 넣으면 **한글(HWPX/HWP)·워드(DOCX)** 문서로 떨어진다.

- **입력:** 문항 풀(NE_POOL 구조의 JSON/JS) — 그룹별 발문(`ask`) + 항목들(`q`, `ans` 등)
- **출력:** `.hwpx`(한글 2014+), `.docx`(워드), `.hwp`(구버전 한글 2007~2010)
- **뷰 모드 4종:** 문제 / 정답(정답만) / 문제(스펠링) / 문제+정답(정답표시 시험지)
- **레이아웃:** 1단·2단 × 글자 9/11/13pt × 줄간격(툴바 3단계: 좁게/보통/넓게)
- **동작 전제:** 라이선스·서버 없이 브라우저(`file://`) 또는 순수 Python에서 생성 (§14)

## 1. 세 가지 출력 형식 — 방식이 다르다 (★핵심)

세 포맷은 **변환 체인이 아니라 병렬 생성**이다. 하나의 문항 데이터로 각각 독립 생성한다.

| 형식           | 확장자 | 정체               | 생성 방식                                         | 대상                                                | 생성기                                                  |
| -------------- | ------ | ------------------ | ------------------------------------------------- | --------------------------------------------------- | ------------------------------------------------------- |
| **HWPX** | .hwpx  | zip + OWPML(2011)  | 정본 18개<br />**section0 본문교체**        | 한글 2014+                                          | hwpx-tpl-export.js (브라우저) / gen_section.py (검증용) |
| **DOCX** | .docx  | zip + OOXML        | 정본 18개<br />**word/document.xml만 교체** | MS Word                                             | docx-tpl-export.js                                      |
| **HWP**  | .hwp   | HWPML 2.8 단일 XML | **from-scratch 조립**(템플릿 없음)          | 구버전 한글<br />(2007~2010, HWPX 미지원 2014 미만) | hwpml-export.js                                         |

> **정본 개수 = 단(2) × 크기(3) × 줄간격(3) = 18개** (2026-07-23 확정). 원래 줄간격 5단계(매우좁게~매우넓게)라 30개였으나, 슬라이더가 3단계(좁게/보통/넓게)로 축소(2026-07-22)되며 코드가 3단계만 참조 → **매우좁게·매우넓게 12개는 미참조**. **HWPX·DOCX 모두 미참조 12개를 디스크에서도 삭제 → `templates/`·`docx/`·`templates.js`·`docx-templates.js` 전부 18개.**

### 데이터 삽입 — 어떤 태그로 어떻게 넣나

세 포맷 모두 **문단 = 1항목/1발문**을 단위로, 텍스트 태그에 단어·뜻·정답을 문자열로 넣는다. 서식(글꼴·밑줄·줄간격)은 태그가 아니라 **ID 참조** 방식(HWPX·DOCX)이거나 문서 내 정의(HWP)다.

| 형식           | 데이터 넣는 곳                      | 문단·런·텍스트 (실데이터)                                                        | 답란 우측정렬                                                 | 줄바꿈(다줄·긴답)  | 2단(다단)                                    | 서식 정의 위치                                                                                                                                                                                         |
| -------------- | ----------------------------------- | ---------------------------------------------------------------------------------- | ------------------------------------------------------------- | ------------------- | -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **HWPX** | `Contents/section0.xml` 본문교체  | `<hp:p paraPrIDRef>` › `<hp:run charPrIDRef>` › `<hp:t>텍스트</hp:t>`      | `<hp:tab type="2" width>`(폭 자기보정) + tabPr RIGHT 정지점 | `<hp:lineBreak/>` | `<hp:colPr type="NEWSPAPER" colCount="2">` | **별도 `header.xml`** — paraPr/charPr가 ID로 정의(밑줄 charPr·발문간격 paraPr는 런타임 추가)                                                                                                 |
| **DOCX** | `word/document.xml` 본문교체      | `<w:p><w:pPr>` › `<w:r><w:rPr>` › `<w:t xml:space="preserve">텍스트</w:t>` | `<w:tab/>` + `<w:tabs><w:tab w:val="right" w:pos>`        | `<w:br/>`         | `<w:cols w:num="2" w:space>`(sectPr)       | 문단·런 안에**인라인**(`<w:pPr>`/`<w:rPr>`). 밑줄=진짜 서식 `<w:u w:val="single">`(정답표시)·`_`문자(문제), 줄간격 `<w:spacing w:line lineRule="auto">`, 문단보호 `<w:keepLines/>` |
| **HWP**  | 단일 XML**from-scratch** 조립 | `<P>` › `<TEXT>` › `<CHAR>텍스트</CHAR>`                                   | `<TAB/>`(RIGHT 정지점 2×클램프) + `<UNDERLINE>` 속성     | `<LINEBREAK/>`    | `<COLDEF Type="Newspaper">`                | 문서 내`<PARASHAPE>`/`<CHARSHAPE>` 정의(로고박스는 플로팅 `<TABLE>`)                                                                                                                             |

- **공통 구조:** `문단(paraPr) › 런(charPr) › 텍스트`. HWPX·DOCX는 **정본에 이미 있는 서식 ID를 참조**만 하고 본문 태그만 새로 찍는다(그래서 "본문교체"). HWP는 서식 정의까지 코드가 함께 만든다(그래서 "from-scratch").
- **밑줄 차이:** HWPX·HWP는 `_` 실문자('맑은 고딕')로 그림(공백 밑엔 밑줄이 안 그려지는 한글 특성 §12-2). DOCX만 `<w:u>` 진짜 밑줄서식이라 nbsp 밑에도 그려짐.

**한 줄 요약:** HWPX·DOCX는 "검증된 정본을 두고 본문만 갈아끼운다". HWP는 "코드가 XML을 처음부터 통째로 만든다".

### 왜 "본문교체"인가 (from-scratch 폐기 이력)

- 초기에는 HWPX를 좌표까지 코드로 통째 조립 → paraPr/charPr/tabPr/colPr 좌표가 한글 기대치와 미세하게 어긋나 **"열리지만 깨짐"** 반복 → **폐기**.
- 이후(현재 방식) **검증된 정본 18개의 section0.xml 본문만 교체**. 나머지(header·settings·mimetype…)는 바이트 그대로. 스타일 ID는 정본에서 추출·재사용 → "열리지만 깨짐" 오류군이 통째로 사라짐.

### 왜 .hwp만 확장자 다른 XML(HWPML)인가

- HWPML 2.8은 2000년대 초부터 지원된 구식 XML이라 **구버전 한글도 연다**. 반면 hwpx(2011 신식 zip)는 한글 2014+만 연다.
- 한글은 **확장자가 아니라 내용을 보고** 열어주므로, 구버전 호환용으로 HWPML을 `.hwp` 확장자로 내보낸다.

## 2. 두 개의 생성 트랙 + 백엔드 전달

| 트랙                          | 위치(이 저장소)          | 실행 환경                                  | 언어       | 용도                                  |
| ----------------------------- | ------------------------ | ------------------------------------------ | ---------- | ------------------------------------- |
| **브라우저 생성기**     | 저장소 루트(`index.html`·`*-export.js`) | 위저드 웹앱, `file://` 가능   | JavaScript | 실서비스 다운로드 버튼(**주 산출물**) |
| **검증용 생성기 (CLI)** | `validation/` | 순수 Python(`build.py`), 브라우저 불필요 | Python     | **검증 레퍼런스·오라클**(§10, 선택) |

> 두 생성기를 **브라우저 생성기**(실서비스, 루트)·**검증용 생성기**(정확도 대조, `validation/`)로 부른다. 원본 프로젝트에선 각각 `…-v2.6/`·`…-v2.7/` 폴더였으나, 이 배포 저장소에선 루트·`validation/`으로 통합했다.

- 검증용 생성기의 HWPX 코드 `gen_section.py`는 브라우저 생성기 `hwpx-tpl-export.js`를 **충실 이식**한 것 — 같은 입력 → 같은 출력(오라클 diff **30/30 바이트 일치**).
- 검증용 생성기 발상: 정본 파일들(HWPX 18개, DOCX 실참조 18개)은 손 관리로 표류가 낀 파일들. 본질은 **스켈레톤 6개(1·2단 × 9/11/13pt) + 줄간격은 header.xml 숫자 주입**만으로 커버.
- .docx / .hwp는 현재 브라우저 생성기 JS(`docx-tpl-export.js` / `hwpml-export.js`)가 담당하며, **DOM 없이 Node에서 직접 구동**된다(오라클로 실증: `buildSection0`·`buildHwpml`을 `require` 후 인자만 넘겨 호출).
- 포팅 함정(기록됨): JS `.replace`(첫 매치만)=`re.sub(count=1)`, `Math.round`=`floor(x+0.5)`, `normalizePool` 선행.

### 백엔드 전달 방식 — Next.js + NestJS 전제

백엔드 스택은 **NestJS(Node/TypeScript)**. 이 **기정 스택을 전제로** 보면, 전달물은 **검증용 Python 생성기가 아니라 "헤드리스 Node용으로 정리한 JS 엔진"** 이 맞다. (즉 새로 내린 결정이 아니라, 정해진 스택에 맞춘 자연스러운 귀결.)

- 이유: 생성기 원본이 **이미 JS**(`*-export.js`)이고, DOM 없이 **Node에서 그대로 실행**된다(오라클로 증명). 기정 스택이 Node인데 Python을 붙이면 크로스-언어(subprocess/마이크로서비스)라 런타임 2개·배포 복잡도가 는다.
- 이점: **docx·hwp를 Python으로 재이식할 필요가 없다**(세 포맷 다 JS로 이미 존재). NestJS 안에 모듈로 포함 → 단일 런타임.
- 헤드리스화 작업: ① 입력 DOM 제거(`readConfig()`의 `document` 읽기 → 함수 인자 JSON), ② `JSZip`(Node 동작) 유지 · `saveBlobCompat` → **`Buffer` 반환**, ③ (선택) TypeScript 포팅.
- **검증용 Python 생성기의 위치:** 폐기가 아니라 **검증 자산** — JS 리팩터 시 "이 생성기 출력과 바이트 일치"로 회귀 검증(오라클, §10). 후일 Python 서비스가 필요하면 재사용.

> 요약: **전달 = 헤드리스 JS/TS 엔진(NestJS 내), 검증 = 검증용 Python 오라클.** (검증용 생성기를 그대로 백엔드에 올리는 방향은 스택 불일치라 지양.)

## 3. 템플릿 저장 구조

### HWPX — `templates.js`

- `window.HWPX_TEMPLATES = { "파일명.hwpx": { "Contents/header.xml": \`...\`, "Contents/section0.xml": \`...\`, ... } }`
- 정본 내부 XML을 **base64가 아니라 텍스트 그대로** 담음 → grep·직접수정 가능.
- 런타임(브라우저 `file://`)이 이걸 읽어 zip을 즉석 조립 → **서버 없이 동작**([hwpx-tpl-export.js:978](hwpx-tpl-export.js#L978)).
- 원본 폴더 `templates/*.hwpx`(**18개** — 매우좁게·매우넓게 백업 12개는 2026-07-23 삭제)는 **편집용 원본**. 수정 후 `tools/build-templates-js.py`로 재생성. 역복원은 `tools/extract-templates-from-js.py`.

### DOCX — `docx-templates.js`

- `window.DOCX_TEMPLATES = { "파일명.docx": "<base64>" }` — docx를 **통째로 base64**.
- 원본 `docx/{단}단/{크기}/*.docx`(**18개** — 매우좁게·매우넓게 백업 12개 삭제). 재생성 `tools/build-docx-templates.py`.

### HWP — 없음

- `hwpml-export.js`가 HWPML 2.8 단일 XML을 코드로 생성. 템플릿·정본 참조 0건.

### ★자기완결성

**실행/배포엔 `templates.js`·`docx-templates.js`만 있으면 된다.** 원본 폴더(`templates/`, `docx/`)는 유지보수용 백업. (단 정본을 고치려면 원본 폴더에서 고치고 재생성하는 게 정석.)

> **★한 줄 요약 (제작 근거):** **헤더는 `print_sample_0722`(최종 인쇄본)를 참고**해 코드로 재조립하고, **본문(콘텐츠·레이아웃)은 기존에 참고하던 정본 템플릿(18개)을 참고**해 만든다. 즉 두 부분의 출처가 서로 다르다.

| 구성요소                                 | 기준(정본) 위치                                                                                          | `print_sample_0722` 참조?                       |
| ---------------------------------------- | -------------------------------------------------------------------------------------------------------- | ------------------------------------------------- |

> **헤더와 `print_sample_0722`의 관계 (★자주 헷갈리는 지점):** 헤더는 **`print_sample_0722`를 "설계 기준"으로 참고해 그 구조(2줄 배치·로고박스·구분선)를 코드에 반영**했다(§7.5). **런타임에 print_sample 파일을 읽지는 않으며, 정본 템플릿의 헤더도 쓰지 않는다**(코드 재조립본으로 대체). 비유하면 print_sample은 설계도, 코드는 그 설계도대로 찍어내는 금형 — 금형은 설계도를 보고 만들어졌지만 찍을 때마다 설계도를 다시 꺼내보진 않는다. 텍스트(학원·반·날짜·교재·제목)만 위저드 입력으로 매번 채운다.

`.hwpx`는 OCF(zip)다. 핵심 멤버:

| -------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- | ------------------------------------------- |
| `Contents/section0.xml`                                                        | **본문**(문단들). 페이지설정 secPr는 첫 문단 안에 있음                       | ✅ 본문 재생성                              |
| `Contents/header.xml`                                                          | **서식 창고** — 글꼴·크기·자간·줄간격·문단속성·밑줄 charPr/paraPr 정의 | ✅ 밑줄·발문간격 charPr/paraPr 런타임 추가 |

- **페이지설정(용지·여백·테두리·각주)** = section0 첫 `<hp:p>`의 첫 run `<hp:ctrl><hp:secPr>` 안. (별도 파일 아님)

## 5. 데이터 모델

문항 데이터 = **그룹 배열**. 각 그룹 `{ ask(발문), full(1단 여부), items[] }`, 각 항목 `{ q, wl, aw, a }`.

- `q` — 발문/단어/뜻(HTML: `<b>`, `<br>`, `<span class="wl" data-ans data-fl>` 빈칸 마커)
- `wl` — 줄 끝 답란 유무 · `aw` — 영어 답 · `a` — 우리말 답
- 정규화(`normalizePool`): `aw`/`a` → 내부 `ans`/`fl`(첫 글자)로 매핑, 통번호 `_n` 부여
- **후미배치(`neReorderFullLast`):** 1단 유형(full=true: 문장완성·영영풀이)을 **항상 맨 뒤로** 재배치 + 재번호 → 취약한 "전체폭→2단 경계"를 구조적으로 제거

검증용 생성기는 이 구조를 `content.json`으로 그대로 받는다.

## 6. 본문 생성 파이프라인 (HWPX 기준)

```
content(JSON) → normalizePool → neReorderFullLast → buildSection0 → prefix + 생성문단 + suffix
                (번호매김)      (1단유형 후미배치)   (프로파일+생성)
```

1. **normalizePool** — 항목에 통번호 `_n` 부여, `ans`/`fl` 보정 ([gen_section.py:1022](validation/gen_section.py#L1022)).
2. **neReorderFullLast** — 1단 유형(문장완성·영영풀이)을 **항상 맨 끝**으로 재정렬+재번호 ([:1040](validation/gen_section.py#L1040)).
3. **splitSection** — section0을 `prefix`(=`<hs:sec>`) / `body`(문단들) / `suffix`(=`</hs:sec>`)로 3분할 ([:93](validation/gen_section.py#L93)).
4. **profileTemplate** — 정본 본문 샘플 문단에서 스타일 ID(itemPP/itemCP/fullPP/colPr2/blankRun/탭앵커) 추출 ([:406](validation/gen_section.py#L406)).
5. **normalizeHeader** — header.xml **수정**: keepLines 0→1, snapToGrid 1→0(전역), 정답 밑줄 charPr·발문간격 paraPr 추가 ([:358](validation/gen_section.py#L358)).
6. **buildSection0** — 헤더 문단 보존(제목만 치환) + 발문·항목 문단 생성. 2단 분할·페이지나눔 계산 ([:864](validation/gen_section.py#L864)).

**즉 실제 재생성 영역 = 첫 발문(`※`)부터 마지막 항목까지.** 그 앞(제목·이름/점수표·secPr)은 보존.

### 페이지 나눔/2단 분할은 "계산"이다

페이지가 어디서 넘어가고(2페이지·3페이지…), 2단일 때 몇 번 문항에서 왼쪽 칸→오른쪽 칸으로 넘어가는지는 **고정값이 아니라 매 요청마다 계산되는 결과**다.

- `pageTextHeight` ÷ 줄높이 → `pageCapLines`(페이지당 줄수 상한) ([:906](validation/gen_section.py#L906)).
- `estItemLines`(항목별 줄수 추정) → `splitAt`(2단 좌우 균형 분할점) ([:983](validation/gen_section.py#L983)).
- 각 문단에 `colBreak`/`pageBreak` 플래그 부여 ([:1013](validation/gen_section.py#L1013)).

**★"정적 복사 불가"의 뜻** — 완성된 결과 파일(또는 문단 덩어리)을 **미리 만들어 두고 요청 시 그대로 복사**해 내보내는 방식은 쓸 수 없다는 것. 이유:

- 분할점 계산은 **이번에 넣는 문항의 수·크기에 전적으로 의존**한다. 문항이 30개냐 31개냐, 뜻이 길어 2줄이 되느냐 1줄이냐에 따라 `splitAt`·`pageBreak` 위치가 달라진다.
- 예: 30문항이 "15번에서 오른쪽 칸으로 넘어가고 2페이지로 나뉨"이었는데 **문항 하나만 추가(31문항)** 하면 분할점이 16번으로 밀리고 페이지 경계도 이동한다 → 30문항용으로 미리 만든 파일을 31문항에 재활용하면 레이아웃이 전부 어긋남.
- 그래서 **매 요청마다 문항을 넣고 처음부터 계산·조립**해야 한다(동적 생성).

> 혼동 주의: 정본 템플릿(18개)을 "복사해 쓴다"는 건 **문항이 안 들어간 빈 서식 틀**(페이지설정·스타일·헤더)을 재사용한다는 뜻이고, 그 틀 안에 들어가는 **본문(발문~마지막 항목)은 항상 새로 생성**된다(§6 "실제 재생성 영역"). 서식 틀 재사용 ≠ 결과물 정적 복사.

## 7. 확정된 레이아웃 원칙

### 7.1 2단 = 표 없는 "신문형 다단"

- 2단은 **표가 아니라 신문형 다단**(HWPX `colPr` / DOCX `w:cols` / HWPML `COLDEF Type="Newspaper"`).
- **표(table)는 폐기:** 레이아웃·분할은 완벽하나 **한글에서 복사 시 셀이 평면화돼 문항 순서가 꼬임**(되돌리지 말 것). 레거시 `createHWP.asp`도 신문형 다단 사용.
- 발문(ask)은 `colCount=1`(전체폭)로 단일단 영역에 얹음.

### 7.2 답란 밑줄 — 우측정렬 + 복사 가능

| 포맷 | 밑줄                                            | 우측정렬                                                       |
| ---- | ----------------------------------------------- | -------------------------------------------------------------- |
| HWPX | 실제`_` 문자 연속선('맑은 고딕')              | `type=2` 탭 width 자기보정 + tabPr RIGHT 정지점              |
| DOCX | 실제`_` 문자(문제) / 서식 밑줄+nbsp(정답표시) | 우측탭(`w:val="right"`)                                      |
| HWP  | UNDERLINE 속성 + nbsp                           | RIGHT 정지점 =**2×가용폭 클램프** + 긴 내용 수동 줄바꿈 |

- 공백/nbsp 밑줄은 HWP 복사 시 사라져 → **`_` 실문자**라야 복사됨(HWPX/DOCX).
- 답란 `_` 밑줄은 **'맑은 고딕' 폰트**로 찍어야 한글·폴라리스·웨일 다 연속선. 함초롬바탕 `_`는 틈남.

### 7.3 긴 답 처리 — 새 줄 우측정렬 (2026-07-22 3포맷 통일)

- 답이 **고정 밑줄칸을 넘으면**(예: `counterrevolutionary`·`extraterrestrial`), 뜻 뒤에 붙이지 않고 **답만 새 줄로 내려 우측정렬**한다(`overflow` 판정 → `<hp:lineBreak/>` / `<w:br/>` / `<LINEBREAK/>`).
- 칸에 들어가는 답(≤ 슬롯)은 인라인 우측정렬 유지.
- HWPX·DOCX는 2026-07-22에 이식해 세 포맷이 일관됨. **HWP는 새 줄 우측정렬 시 선행 탭 2개 필요**(tab1→LEFT@HANG 정지점 소비, tab2→RIGHT 정지점 도달).
- 긴 **뜻**은 왼쪽 영역 폭 안에서 코드가 수동 줄바꿈(`emitMeaningWrapped` / `charWrap` / `wrapText`) → 밑줄 영역 침범 방지.

### 7.4 기타 정렬

- 유의어/반의어 `(유)`/`(반)` 마커는 **밑줄 바로 왼쪽**에 붙어 답과 한 덩어리로 우측정렬.
- 정렬은 왼쪽 정렬(Justify 금지 — 답란 밑줄 줄바꿈 시 첫 줄 늘어짐).
- 서식은 민무늬(크기·구조만) — 볼드/기울임은 화면 미리보기에서만.

### 7.5 헤더 — 동적 2줄 조립 (2026-07-22, print_sample 최종 반영)

- 최종 인쇄본(한글 저장 바이너리 hwp) 헤더가 **2줄 구조**라 이를 정본으로 삼음:
  - **line1** = `{학원}·{반}·출제일 {날짜}[{교재}]`
  - **line2** = `{제목}   이름 ____ | 점수 ____`
- 위저드 입력 필드(학원·반·날짜·교재·제목)로 **동적 조립**(치환이 아니라 조립).
- **HWPX:** `gen_section.build_header_block()` — 스켈레톤 첫 문단의 `secPr`(페이지 설정) 보존하고 `<hp:t>`만 line1로 교체 + line2 조립. `build.py --academy/--klass/--date/--book/--title`. 필드 없으면 기존 동작(제목만 치환).
- **HWP(HWPML):** `hwpml-export.js` addHeader 2줄 + `date` 필드 + 헤더 아래 가로 구분선. 좌측 로고 박스(플로팅 1×1 표, 20mm)는 **회색 점선**(#7F7F7F Dash, BorderFill id5)으로 그리며 **구버전 한글 실렌더 확인 완료**(2026-07-23, 박스 안 잘림·구분선 박스 아래 일자).
- **DOCX:** **완료** — `docx-tpl-export.js`의 `buildDocxHeader()`로 코드 재조립(HWP/HWPX와 동일 규칙). line1(학원·반·출제일 날짜[교재]) + 로고박스(14mm) + line2 + **full-width 구분선**. 종전 템플릿 보존(`prof.titleParas`) 대신 재조립본 사용, `readConfig`가 academy·cls·book·date·title 읽음. 박스 14mm 축소·구분선 full-width는 Word 렌더 육안 확인 완료(2026-07-23). ※"예시 파일 수령 후 정본 교체" 대신 코드 재조립으로 처리 → 정본 파일·재생성 불필요.

## 9. 줄간격 · 글자크기 · 문항간격 (SSOT)

- **글자크기** 9/11/13pt, **단수** 1/2단 → 스켈레톤 6종의 진짜 구조 분기(header의 colPr·charPr 세트).
- **문항간격:** 툴바 3단계(좁게/보통/넓게). `ne-export-common.js`의 `NE_GAP_PX=[11,18,27]`·`NE_GAP_NAMES`. level 0=좁게 1=보통 2=넓게.

### 9.1 줄간격 — 엔진마다 값과 출처가 다르다 (★함정, 2026-07-23 확정)

줄간격 %는 **엔진별로 다른 값**을 쓴다. **같은 % 숫자라도 한글(HWPX)이 워드/구형한글보다 촘촘하게 렌더**되기 때문이다(아래 표의 두 소스 함수).

| 포맷                  | 쓰는 값(함수)                                     | 9 / 11 / 13pt (좁게·보통·넓게)                                     | 주입 방식                                                                                                                   |
| --------------------- | ------------------------------------------------- | -------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| **.hwp**(HWPML) | `neVocabLineSpacing` (HWPX와 동일, 한글 검증값) | 9`[145,155,170]` · 11 `[150,160,180]` · 13 `[165,170,190]`   | `cfg.ls`로 본문 문단에 직접 주입                                                                                          |
| **HWPX**        | `neVocabLineSpacing` (정본 템플릿/OWPML 값)     | 9`[145,155,170]` · 11 `[150,160,180]` · 13 `[165,170,190]`   | 템플릿 로드 + 본문 paraPr`lineSpacing`에 명시 주입(`overrideBodyLineSpacing` / 검증용 생성기는 `inject_line_spacing`) |
| **DOCX**        | `neVocabHwpLineSpacing` × 2.4 (twips 근사)     | 9`[90,105,135]` · 11 `[85,100,130]` · 13 `[80,95,125]` ×2.4 | item/발문 문단에`w:line`(lineRule=auto) 주입, `w:after` 유지                                                            |

- **왜 "같은 % 숫자"를 못 쓰나 — RATIO vs Percent 렌더 차:** 줄간격 %는 **형식마다 실제 렌더 폭이 다르다.** ① **OWPML(.hwpx) PERCENT는 HWPML(.hwp)보다 촘촘**(2026-07-23, 세 포맷을 `.hwp` 실측값으로 통일했더니 HWPX가 눈에 띄게 좁아짐 → HWPX는 정본 템플릿값 유지). ② **.hwp 정본 바이너리(OLE)는 item 문단이 `RATIO(글자에 따라)` 85/100/130%인데, 이를 HWPML `Percent`로 그대로 쓰면 더 촘촘하게 렌더돼 정본보다 좁아진다**(2026-07-23 사용자 확인: 정본 `vocab_1col_11_narrow.hwp`이 생성물보다 넓음). → **`.hwp`도 `print_sample` 실측 숫자(85/100/130) 대신 한글에서 검증된 `neVocabLineSpacing`(11pt 150/160/180)으로 전환.** 결과: **`.hwp`·HWPX가 같은 값**을 쓰고, **DOCX만** 아직 `neVocabHwpLineSpacing`(85/100/130)×2.4를 쓴다(Word는 또 다른 렌더러). 핵심 교훈 = **"정본의 숫자"가 아니라 "정본의 보이는 간격"을 맞춰야 한다.** (DOCX도 좁게가 답답하면 동일하게 `neVocabLineSpacing`으로 전환 검토.)
- **런타임 주입이라 템플릿 재생성 불필요:** 줄간격 값은 세 포맷 모두 **생성 시점에 header/document XML로 주입**된다. 단 HWPX는 템플릿 **파일 선택**에 여전히 `neVocabLineSpacing`의 %(파일명 `…(N%).hwpx`)를 쓰므로, 그 파일이 실재하는 범위 안에서만 값을 바꿀 수 있다.
- **줄간격 주입 위치:** header.xml 본문 paraPr의 `lineSpacing`(%) 숫자. section0에는 줄간격 없음(한글이 열 때 lineseg 재계산).
- 규칙 단일 소스 = `ne-export-common.js`(`neVocabSize`·`neVocabGapLevel`·`neVocabLineSpacing`·`neVocabHwpLineSpacing`·`neReorderFullLast`).
- ⚠️ `.hwp`·HWPX는 값이 같아졌고 **DOCX만 다른 소스**라, **한글/Word 육안으로 세 결과가 비슷하게 보이는지 최종 확인 필요**(§16). `.hwp` 150/160/180 전환은 사용자 확인 완료(2026-07-23, 정본 대비 답답함 해소).

### 9.2 print_sample 실측 vs 생성기 값 — 숫자는 다르지만 의도된 차이 (2026-07-23 실측)

`print_sample_0722`의 `.hwp`(1col) 본문 item 문단 줄간격을 `pyhwp`로 실측한 값과, 현재 생성기가 실제로 내보내는 값은 **숫자가 다르다.** 이건 오류가 아니라 §9.1의 RATIO↔Percent 보정을 적용한 **의도된 차이**다.

| 구분                                 | 줄간격 타입        | 9pt (좁게/보통/넓게) | 11pt (좁게/보통/넓게)     | 13pt (좁게/보통/넓게) |
| ------------------------------------ | ------------------ | -------------------- | ------------------------- | --------------------- |
| **print_sample `.hwp` 실측** | RATIO(글자에 따라) | 90 / 105 / 135       | **85 / 100 / 130**  | 80 / 95 / 125         |
| **현재 `.hwp` 생성기 출력**  | Percent            | 145 / 155 / 170      | **150 / 160 / 180** | 165 / 170 / 190       |

- print_sample 실측값(85/100/130 등)은 SSOT의 `neVocabHwpLineSpacing`과 **정확히 일치** — 즉 print_sample이 그 함수의 출처다.
- 그런데 print_sample은 **RATIO 타입**, 생성기 HWPML은 **Percent 타입**이라 **같은 숫자를 Percent로 넣으면 더 촘촘하게 렌더**된다(정본보다 좁아짐). 그래서 **"보이는 간격"을 맞추려고 숫자를 올려** `neVocabLineSpacing`(11pt 150/160/180)으로 전환했다.
- **핵심:** "정본의 숫자"가 아니라 "정본의 보이는 간격"을 맞춘 것 → 숫자 불일치는 정상. 사용자 육안 확인(2026-07-23, 정본 대비 답답함 해소)으로 정합 확인.

## 12. 알아야 할 제약·함정 (hard limits)

1. **HWPX는 section0만 바꾸면 안 된다** — 정답 밑줄·자간·발문간격이 런타임에 **header.xml로 주입**됨. header.xml을 함께 처리하거나 정본에 pre-bake 필요.
2. **정답 밑줄 폭 균일화 불가** — 한글은 밑줄 서식을 어떤 공백(nbsp·일반공백) 아래에도 안 긋는다(3회 확인·확정). 여백으로 폭 균일화 시도는 전부 실패. `_` 글리프로 채우면 폭은 맞지만 세로위치 단차 발생 → 거부. **HWPX(한글)에서 불가.** (DOCX는 진짜 밑줄서식이라 nbsp 밑에도 그려짐 — 이 이슈 없음.) 재시도 금지 목록: nbsp여백 / 일반공백여백 / border+`_`혼용(단차).
3. **2단 다줄 항목은 컬럼 경계에서 갈라짐** — keepLines가 컬럼 분할은 못 막음. **HWPX(최신 한글)** 만 발생, HWP(구버전)는 KeepLines 존중해 안 갈라짐. 그래서 키 큰 유형(문장완성·영영풀이)은 1단으로 빼고 맨 뒤 배치(§5 후미배치). 완전 해결책(표·1단 전환)은 각각 복사꼬임·2단포기로 거부됨.
4. **뷰어 호환 대상 = 한글(HWP)** — 폴라리스·웨일은 무시. `hp:switch`의 `EDGE_PB_FULL_TO_TWOCOL` 등은 한글 필수라 제거 금지.
5. **정답 긴 답(2단 밑줄칸 초과)** — 새 줄 우측정렬로 처리(§7.3). 답이 컬럼 폭 자체보다 길면 소프트랩 불가피. 한글 육안확인 일부 미완.
6. **답란 `_` 밑줄은 '맑은 고딕' 폰트로**(§7.2).

## 13. 자주 궁금해할 질문 (FAQ)

**Q. 왜 표(table)를 안 쓰고 신문형 다단(colPr)으로 2단을 만드나?**
표 방식은 복사 시 꼬임 발생 → **폐기(되돌리지 말 것)**. 2단은 표가 아니라 신문형 다단(colPr). 발문은 전체폭.

**Q. 왜 한컴 공식 hwpxlib(Java)로 생성 안 하나?**
hwpxlib는 "valid HWPX 쓰기"를 대신할 뿐, 우리 실제 문제인 **한글 렌더러의 레이아웃 충실도**(탭폭·줄바꿈·2단 분할)는 그대로 우리 몫. 게다가 Java라 브라우저 `file://`에서 못 돎(서버 필요) → 배포 전제 붕괴. 우리 버그는 XML 유효성이 아니라 레이아웃/데이터 문제라 라이브러리 교체로 안 사라짐.

**Q. 정답을 인라인 좌측배치로 바꾸면?**
가능. 타사(동아) 정답본이 이 방식(우측정렬 없이 프롬프트 뒤 인라인 밑줄, 가변폭 수용). 우측정렬을 버리면 "2단 밑줄칸 초과→왼쪽 흐름" 문제도 자동 소멸. (검토만, 미적용)

**Q. 왜 `file://`(서버 없이)로 동작해야 하나?**
사용자가 로컬에서 파일만 열어 쓰는 게 요구사항. 그래서 정본을 templates.js에 내장(base64/텍스트)해 fetch 없이 동작.

**Q. HWP(.hwp)는 왜 따로 있나?**
구버전 한글(HWPX 못 여는 2014 미만) 호환용. HWPML 2.8 단일 XML from-scratch. 구형한글 실기기 육안확인은 일부 미완.

**Q. 손편집한 서식이 재생성 때 반영 안 되는데?**
의도된 동작. HWPX는 민무늬(크기·구조만) 정책, 미리보기만 볼드/기울임 유지. (방법 A 폐기)

## 14. 라이센스·SDK 의존성 — 무료·무서버가 "가능"하다 (강점, 절대원칙 아님) (★)

**생성·배포·자동검증 파이프라인 전체가 유료 SDK도, 한글(한컴오피스) 라이센스도, 서버도 없이 완결 가능하다.** 이는 진입장벽 0(로컬·PoC·오프라인 배포에 유리)이라는 **강점**이지, 서버·라이선스를 금지한다는 원칙은 아니다. 실서비스로 갈수록 라이선스를 **선택적 업그레이드**로 붙이는 게 자연스럽다(§14-후반). (서버화는 AX팀 후속, §16.)

### 생성 (라이센스 0건)

- **순수 텍스트/XML 조립.** 한컴 공식 SDK·hwpxlib(Java)·유료 라이브러리 **사용 0건**. 정본의 XML 문자열을 자르고 붙이는 것뿐(§1·§6).
- **실행 런타임도 무료:**
  - 브라우저 생성기 = 브라우저 `file://`에서 도는 순수 JavaScript. 설치·서버·라이센스 없음.
  - 검증용 생성기 = Python **표준 라이브러리만**(외부 유료 패키지 없음).
- **포맷 명세가 전부 공개 스펙**이라 리버싱이나 유료 SDK가 불필요:
  - **HWPX = OWPML** — 한컴이 공개한 개방형 문서 표준(KS 표준으로 공개).
  - **DOCX = OOXML** — ECMA-376 / ISO 공개 표준.
  - **HWP = HWPML 2.8** — 한컴이 공개한 XML 포맷 문서 기반.

### 자동 검증 도구 (전부 오픈소스/무료)

| 도구                    | 용도                                             | 라이센스    |
| ----------------------- | ------------------------------------------------ | ----------- |
| `python-hwpx`         | `.hwpx` 열림(구조 유효성) 검증                 | 오픈소스    |
| `python-docx`         | `.docx` 열림 검증                              | 오픈소스    |
| `pyhwp`(`hwp5proc`) | 바이너리`.hwp`에서 ParaShape 줄간격·여백 추출 | 오픈소스    |
| `jsdom`               | Node에서 브라우저 DOM 흉내(다운로드 로직 실행)   | 오픈소스    |
| `xml.dom.minidom`     | XML well-formed 검사                             | Python 표준 |

→ 열림 검증·무회귀(바이트 diff)·줄간격 실측까지 **한글 프로그램 없이** 자동화 가능(§10).

### 라이센스가 필요한 유일한 지점 = 육안 검증(선택)

- 실제 렌더(탭폭·2단 분할·로고 박스 등)를 사람 눈으로 최종 확인하는 것만 **한글 프로그램**에서 해야 한다.
- 그러나 **읽기 전용 확인은 무료 「한글 뷰어」로 충분**하다. 편집·정밀 측정만 유료 한컴오피스.
- 즉 유료 라이센스는 **파이프라인 밖(사람의 눈 검증)**에만, 그것도 대체 가능한 형태로만 걸린다.

**한 줄 요약:** 문항 데이터 → 시험지 파일까지, **돈 드는 것 하나 없이** 로컬에서 끝난다. 한글 라이센스는 "만든 결과가 실제로 예쁘게 뜨나 눈으로 볼 때"만, 그마저 무료 뷰어로 대체된다.

### 그럼 라이선스를 "일부러" 도입하면 뭐가 좋나 (선택적 업그레이드)

무료·무서버는 **하한선**이고, 실서비스에서는 아래 이득을 위해 **라이선스**를 선택적으로 얹는다. (서버화·DB 연동·PDF 출력 등 운영 인프라는 AX팀 후속 범위라 여기서는 다루지 않는다 — §16.)

**라이선스(한컴 공식 엔진/SDK)를 쓰면** — 이득은 **사용자용 정확 렌더 하나가 결정적**이다.

| 이득                                  | 설명                                                                                                                                             | 냉정한 평가                                                                      |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------- |

### 1. 여러 줄 문항이 페이지 넘김에 걸리면 줄 구성이 쪼개짐

예시 문항:

```
34. produce
    [명사] 생산자, 제작자    ____________
    [명사] 생산품, 제품     ____________
    [명사] 생산, 제조       ____________
```

- **현상:** 여러 줄 문항이 페이지 경계에 걸리면, 문항이 넘어가면서 답란이 왼쪽 단을 벗어나 오른쪽 단 위치로 쪼개짐.
- **원인:** 한글이 "문항 줄들을 한 덩어리로 유지하라"는 속성(`keepLines`)을 2단 페이지 넘김에서 제대로 처리하지 못해, 넘어간 문항의 줄과 밑줄 위치가 어긋나게 재배치.
- **확인한 해결 방안:**
  1. 수정 없이 쪼개짐 수용

## 18. HWP 생성 방식 — from-scratch 유지 vs 정본 본문교체 전환 (검토)

현재 .hwp만 **from-scratch**(hwpx·docx는 정본 본문교체, §1). "hwp도 정본을 주면 다른 포맷과 같은 로직으로 갈 수 있나?"에 대한 정리.

### 왜 지금은 from-scratch인가 (효율 판단이 아니라 제약)

1. **hwp는 나중에 붙은 보조 포맷** — 주력은 hwpx/docx. hwp는 "HWPX 못 여는 구버전" 대응 곁가지라 우선순위가 낮아 "정본부터 확보"보다 **"일단 되게"** 가 현실적.
2. **HWPML은 단일 XML이라 from-scratch가 성립** — hwpx from-scratch 폐기는 zip+여러 XML+복잡 좌표 탓. HWPML은 **단일 XML**이라 난이도가 낮아 정본 없이도 "일단 열리는 파일"을 만들 수 있었다. (hwpx였다면 이 길이 막혀 정본을 구했을 것.)

→ 즉 지금 상태는 **PoC 단계의 합리적 선택**이고, **정본(HWPML) 확보 시점이 ②로 갈아탈 타이밍**.

### 가능 여부 = 정본 "형식"에 달림

| 정본 형식                                                       | 본문교체 가능?   | 이유                                                                                                    |
| --------------------------------------------------------------- | ---------------- | ------------------------------------------------------------------------------------------------------- |
| **HWPML(.hml, 텍스트 XML)** — 한글이 "HWPML 문서"로 저장 | ✅**가능** | hwpx/docx처럼 텍스트라 본문 문단만 문자열 교체 가능                                                     |
| **바이너리 .hwp** — 한글 5.0 네이티브                    | ❌ 사실상 불가   | 압축·오프셋 있는 바이너리 복합파일 → 문자열 교체 불가.**이것이 hwp를 from-scratch로 만든 이유** |

→ "hwpx/docx와 동일 로직"은 **정본을 HWPML(.hml) 텍스트로 줄 때만** 성립.

### ① 지금(from-scratch) vs ② 정본 본문교체 전환 (정본=HWPML 전제)

|                 | ① 지금(from-scratch)                                            | ② 정본 본문교체 전환                                     |
| --------------- | ---------------------------------------------------------------- | --------------------------------------------------------- |
| 동작            | 이미 됨(열림·XML 유효)                                          | 재작업 필요                                               |
| 레이아웃 충실도 | **수동으로 다 맞춤**(로고박스·줄간격 실측표·헤더 손튜닝) | **정본에서 검증된 서식 상속** → 손튜닝↓           |
| 코드 구조       | hwpx/docx와**별개**(중복 로직·별도 버그)                  | hwpx/docx와**동일 패턴**(통합)                      |
| 의존성          | 정본 불필요                                                      | 정본(HWPML) 필요 + 구버전 한글이 그 HWPML 열어주는지 확인 |

### 결론

**장기적으로 ②가 더 효율적.** 이 프로젝트가 hwpx에서 이미 겪은 교훈과 동일하기 때문:

> from-scratch hwpx는 레이아웃이 계속 어긋나 폐기 → 정본 본문교체로 "열리지만 깨짐" 사라짐(§1).

**지금 hwp의 from-scratch는 그 폐기된 방식을 반복하는 셈.** 로고박스 미확인·줄간격 실측표 수동·헤더 손조립 부담이 전부 "좌표를 직접 맞춰서" 생기는 것이고, ②로 가면 정본이 이를 물려줌.

**결정적 전제 2개:** (1) 정본을 **HWPML(.hml) 텍스트**로 받을 것(바이너리 .hwp면 불가), (2) **구버전 한글(2007·2010)이 그 HWPML을 실제로 열어주는지** 확인(hwp의 존재 이유가 구버전 호환).

**권고:** 단기(PoC 급하면)는 ① 유지, **본 서비스 지향이면 ②로 전환**. 단 HWPML은 OWPML과 태그 체계가 달라 "완전 동일 코드"는 아니고 **같은 패턴(profileTemplate·본문교체)에 HWPML용 파서만 따로** 붙이는 형태.

### 현재 결정 (2026-07-23): ① from-scratch 유지

- **지금은 ② 전환 안 함, ① 상태 그대로 둔다.** 현재 `.hwp`는 이미 동작·검증 완료(줄간격·헤더·로고박스 사용자 OK)라 급히 갈아엎을 이유가 없다.
- **정본(.hml) 일부 수령해 둠:** `hwp_0723_hml/`에 **1단 9/11/13pt `normal` 3개**(한글에서 HWPML 저장). 나중에 ②로 전환할 때 쓸 자산이며 **현재 코드엔 미반영**.
- ②로 갈 경우 추가로 필요한 것: (1) **2단도 지원하면** 2단 .hml 3개(9/11/13) 추가 수령, (2) 구버전 한글 실열림 확인. **2단 hwp 지원 여부(§17)** 가 정해져야 파일 수(3 vs 6)가 확정된다.
- ★현 상태 유지 시에도 유효한 사실: **헤더=`print_sample_0722` 참고(코드 재조립), 본문=기존 정본 템플릿 참고**(§3 정본 지도). 이건 방식과 무관하게 그대로다.
